# AGENTS.md — правила работы с кодом

Файл для ИИ-ассистентов и разработчиков: как устроен проект, какие
соглашения соблюдать при любых изменениях. Кратко: это server-rendered
админ-панель на MoonShine 4 поверх REST API платформы UniMICE,
бизнес-логики своей нет.

## Жёсткие ограничения (требование заказчика)

- **Никакого «сырого» HTML/JS**: вся логика и вёрстка — на бэкенде через
  компоненты MoonShine. JavaScript допустим только штатный (async-select,
  пагинация/фильтры через GET-параметры). CSS — только при необходимости,
  отдельным файлом, без инлайн-стилей в PHP-коде.
- Экраны не хранят бизнес-данные локально: всё читается из API на каждый
  рендер (справочники — через кеш, см. ниже). Локальная БД — только для
  служебных нужд (кеш, сессии, очереди).

## Структура кода

```
app/
├── MoonShine/
│   ├── Pages/        # экраны админки (Page-классы, метод components())
│   ├── Fields/       # кастомные поля (SafeDate и др.)
│   ├── Support/      # переиспользуемые хелперы (PagePaginator, цвета)
│   └── Layouts/      # меню и лейаут
├── Services/UniMice/
│   ├── UniMiceClient.php        # HTTP-клиент: токен, retry по 401, таймауты
│   ├── ApiResponse.php          # обёртка ответа → DTO/исключение
│   ├── Endpoints/               # один класс = группа эндпоинтов API
│   └── Dto/                     # spatie/laravel-data DTO
└── Http/Controllers/Admin/      # тонкие контроллеры (async-select и пр.)
```

Соглашения:

- Страница читает параметры из `request()->query()`, вызывает endpoint,
  собирает строки и отдаёт компонентам. Без обращений к HTTP/клиенту
  напрямую из страницы — только через endpoint-класс.
- DTO описывают ответы API; незнакомые поля API не ломают рендер
  (nullable + дефолты).
- Справочники (статусы, типы) кешируются **plain-массивом**:
  объекты spatie-data с анонимными классами не переживают serialize
  кеша. Ключ кеша — `unimice.<сущность>.<справочник>`, TTL — час.
- Фильтры серверные, без JS: состояние живёт в GET-параметрах
  (`?status[]=2`, `?type[]=`…), ссылки страниц пагинации его сохраняют
  (см. `PagePaginator`).

## Правила валидации инпутов

Применяются ко всем формам (создание/редактирование):

- Валидация — **только серверная**, через `rules()` у полей MoonShine;
  фронтовую не добавляем (см. ограничения).
- Каждое поле формы имеет явный rule-set: `required`/`nullable`
  по смыслу поля, типовые форматы (`email`, `date`), числа — с
  `min`/`max` по смыслу (участники ≥ 1, звёзды 1–5 и т.п.).
- **Даты — только `date`, без времени**: бэкенд платформы при создании
  заявки учитывает лишь календарный день. Формат хранения/отправки —
  `Y-m-d`. Для дат используется `SafeDate` (не падает на мусорном
  вводе; стандартный `Date` MoonShine падает с TypeError).
- Ошибки валидации — на русском, через `message()` у правил.
- Значения из формы не доверяем: перед отправкой в API приводим типы
  и отбрасываем пустое (null вместо пустой строки).
- 422 от API пробрасывается в форму как ошибки полей, не как общий
  эксепшн (см. обработку в формах создания заявок).

## Конвенции API UniMICE

- Мультиселект-фильтры в query передаются строкой JSON-массива:
  `statusIds=[1,2]` (не `1,2` и не массив — валидация API отвергнет).
- `GET /events` возвращает всю выборку одним ответом (пагинация у него
  клиентская); `GET /suppliers` пагинируется серверно (`page`/`limit`).
- API медленный: таймаут клиента большой, справочники кешируем,
  лишние запросы к API в рендере недопустимы.
- Токен сервисной учётки кешируется; 401 → обновление токена и один
  повтор (реализовано в `UniMiceClient`).

## Тесты

- `php artisan test` — весь набор должен быть зелёным.
- Feature-тесты экранов: `Http::fake` с паттернами `*/auth/login` +
  конкретные пути, вход через `actingAs(MoonshineUser::factory()->create(),
  'moonshine')`, конфиг подменяется в `setUp()`.
- В тестах кеш — `database` (`RefreshDatabase`), чтобы ловить регрессии
  сериализации.
- Новый экран/поведение — с тестами в `tests/Feature/MoonShine/`,
  новый endpoint — с тестами в `tests/Feature/Services/UniMice/`.

## Стиль

- PHP 8.3, `declare(strict_types=1)`, Pint (`./vendor/bin/pint`).
- Комментарии и тексты UI — на русском, коммиты — кратко, по-русски,
  в повелительном наклонении («Добавить фильтр…», «Исправить…»).
- Изменения — пошагово: один логический шаг = проверка в браузере =
  PR в `main` (squash). Ветка `main` защищена правилами репозитория.
